================================================================================
MANUAL E ESTANDARES DE DESARROLLO: PLATAFORMA DE CARPOOLING (PROYECTO: KOPI)
================================================================================

[OBJETIVO GENERAL]
Guiar al agente CLI o modelo de desarrollo en la implementacion, diseño e
infraestructura de software de una aplicacion de carpooling optimizada para
entornos comunitarios/universitarios, garantizando alta confiabilidad,
baja friccion social y una arquitectura tecnica escalable.

--------------------------------------------------------------------------------
1. PRINCIPIOS CRITICOS DE UI/UX (HUMANIZACION DE INTERFAZ)
--------------------------------------------------------------------------------
* REGLA DE ORO DE IDENTIFICADORES:
  - PROHIBIDO mostrar IDs de base de datos (`user_id`, `route_id`, `trip_id`)
    en componentes de interfaz de usuario.
  - OBLIGATORIO sustituir IDs por nombres legibles, abreviaciones humanas o
    contextos espaciales.
    * Incorrecto: "Viaje #4092 con Conductor 88"
    * Correcto: "Viaje a la universidad con Fabian O."
  
* ELEMENTOS DE CONFIANZA SOCIAL (TRUST UI):
  - Modulo de perfil con fotografia obligatoria y clara.
  - Distintivos visuales (Badges) de validacion de identidad (ej. Correo institucional).
  - Campos de afinidad o carrera/facultad visibles en el perfil para romper el hielo.

* MICROCOPIES Y LENGUAJE DE INTERFAZ:
  - Eliminar terminologia tecnica en mensajes de error o alertas.
  - Transformar logs del backend en estados narrativos:
    * Falla de conexion -> "Estamos experimentando problemas de red, reintentando..."
    * Asignacion -> "Buscando compañeros de ruta en tu zona..."

--------------------------------------------------------------------------------
2. ARQUITECTURA DEL FLUJO DE NAVEGACION (USER FLOW)
--------------------------------------------------------------------------------
* ARQUITECTURA DE ROLES DINAMICA:
  - No separar la aplicacion en ejecutables o modulos aislados por rol.
  - Implementar un switch dinamico de rol (Pasajero / Conductor) en la sesion
    del usuario para permitir alternar el comportamiento fluidamente.

* FLUJO DE RESERVA (PASAJERO) - REGLA DE LOS 3 CLICS:
  - Clic 1: Seleccion de Destino/Origen usando autocompletado inteligente con
    puntos de encuentro preestablecidos (ej. Entradas principales, paradas clave).
  - Clic 2: Visualizacion de tarjetas de Coincidencia (Matching Cards) que
    muestran fotos, asientos disponibles, hora exacta y aportacion economica.
  - Clic 3: Confirmacion de solicitud de asiento con notificaciones Push en tiempo real.

* FLUJO DE PUBLICACION (CONDUCTOR):
  - Permitir guardar y precargar "Rutas Frecuentes" (ej. Casa -> Campus).
  - Selector numerico intuitivo para capacidad de asientos (1 a 4).
  - Boton de accion rapida: "Publicar y salir ahora".

--------------------------------------------------------------------------------
3. ARQUITECTURA Y LOGICA DE SOFTWARE (BACKEND & DATA)
--------------------------------------------------------------------------------
* MODELO DE DATOS Y NORMALIZACION:
  - Tablas Core minimas: Usuarios, Vehiculos, Rutas (Puntos geometricos/Waypoints),
    Viajes (Instancia temporal de una ruta) y Reservas (Transaccion Pasajero-Viaje).
  - Maquina de Estados Rigida para Viajes:
    [Programado] -> [En Curso] -> [Completado / Cancelado]
  - La UI debe suscribirse o consultar estos estados de forma sincronizada.

* GEOLOCALIZACION Y MATCHING OPTIMIZADO:
  - Evitar websockets o rastreo GPS intensivo en background fuera del viaje activo.
  - Utilizar algoritmos de Geohashing o proximidad por radio de coordenadas
    para calcular emparejamientos eficientes en la base de datos sin sobrecargar
    la CPU del servidor.

* RESILIENCIA DEL FRONTEND (MANEJO DE ERRORES SILENCIOSO):
  - Carga asincrona con Skeleton Loaders obligatorios durante la peticion a APIs.
  - Manejo estricto de excepciones: Ante respuestas HTTP 5xx o timeouts,
    la aplicacion debe presentar opciones de reintento local sin romper el flujo.
